# Security hardening implementation plan

Date: 2026-05-31

## Objective

Fix the confirmed security, stability, and deliverability issues found in the auth, user-management, config, store, and deployment review. Prioritize concrete P1 risk reduction before lower-priority hardening.

## Execution order

1. Auth token and session consistency
2. User-management authorization boundaries
3. Production runtime/configuration hardening
4. Container and integration-test reproducibility
5. Contract generation and verification

## Phase 1: Auth token and session consistency

### Files expected to change

- `internal/store/sql/auth_tokens.sql`
- `internal/store/query/auth_tokens.sql.go`
- `internal/store/authrepo/auth_tokens.go`
- `internal/store/authrepo/unit_of_work.go`
- `internal/auth/service/service.go`
- `internal/auth/service/service_unit_test.go`
- `internal/store/authrepo/auth_tokens_integration_test.go`
- Potentially `internal/store/query/models.go` if regenerated by sqlc

### Changes

- Add an atomic one-time auth-token consume query:
  - Match by `purpose`, `token_hash`, `used_at IS NULL`, and `expires_at > now`.
  - Set `used_at` and return the token row in one statement.
- Update `AuthTokenStore` to expose `ConsumeAuthToken` and keep token replay/expiry indistinguishable to clients.
- Use `UnitOfWork` for reset-password flow:
  - Hash the new password before opening the transaction.
  - In one transaction, consume the reset token, update password hash, and revoke refresh sessions.
  - Return internal error if session revocation fails instead of silently succeeding.
- Use `UnitOfWork` for change-password session revocation:
  - Verify current password before transaction.
  - In one transaction, update password hash and revoke refresh sessions.
- Close refresh-token reuse race:
  - If rotation fails because the old token is no longer eligible, revoke the token family fail-closed.
  - Keep client-facing response generic.

### Tests

- Add/adjust unit tests for password change/reset revocation failure.
- Add integration test that consuming the same auth token twice succeeds once and fails once.
- Add/adjust refresh-token race/reuse unit coverage if existing fakes make this practical.

## Phase 2: User-management authorization boundaries

### Files expected to change

- `internal/users/service/service.go`
- `internal/users/service/service_test.go`
- Potentially `internal/store/sql/users.sql`
- Potentially `internal/store/query/users.sql.go`
- Potentially `internal/store/usersrepo/users.go`

### Changes

- Require a system-admin or wildcard actor to mutate a target account that currently has the system-admin role.
- Keep the existing rule that only system-admin or wildcard actors can grant the system-admin role.
- Add last-active-admin protection if the store has enough role data to enforce it cleanly without broad redesign.
- Return a stable forbidden domain error, not a low-level store or SQL error.

### Tests

- Add service tests showing `users:manage` alone cannot update an admin target.
- Add service tests showing non-admin `users:manage` still can update non-admin users within intended boundaries.
- Add last-active-admin tests if implemented in this phase.

## Phase 3: Production runtime/configuration hardening

### Files expected to change

- `internal/config/config.go`
- `internal/config/config_test.go`
- `internal/app/app.go`
- `.env.example`
- `README.md`
- `compose.prod.yaml`

### Changes

- Stop exposing `/metrics` on the main API router in production by default.
- Prefer `METRICS_ADDR` for production metrics scraping.
- Make production compose config pass the project's existing production validations:
  - Secure refresh/access cookies.
  - HTTPS-only explicit frontend origin.
  - No localhost production CORS.
- Document the metrics exposure behavior and production override expectations.

### Tests

- Add config/app tests for production metrics exposure constraints where appropriate.

## Phase 4: Lower-priority hardening

### Files expected to change

- `internal/auth/password/password.go`
- `internal/auth/password/password_test.go`
- `compose.yaml`
- `internal/store/storetest/postgres.go`

### Changes

- Add sane upper bounds to parsed Argon2id password-hash parameters before allocating memory or running verification.
- Bind local development compose ports to `127.0.0.1` instead of all interfaces.
- Pin the PostgreSQL integration-test image more tightly than `postgres:17-alpine` if this can be done without making testcontainers brittle.

### Tests

- Add password verifier tests for rejecting excessive Argon2id memory/time/parallelism values.

## Phase 5: Regeneration and verification

### Generated artifacts

- Regenerate sqlc output if SQL changes are made.
- Regenerate OpenAPI JSON/types only if API contract shapes change.

### Required verification commands

- `make fmt-check`
- `make vet`
- `make test`
- `make openapi-check`
- `make openapi-types-check`
- `make test-integration`

### Integration-test classification

If `make test-integration` fails, classify the failure as one of:

- Code issue: migration/query/service behavior regression.
- Environment issue: Docker unavailable, image pull failure, testcontainers startup failure, port/resource contention.
- Flaky infrastructure: timeout or container readiness race with no code assertion failure.

## Rollout priority

1. Atomic reset-token consumption plus transactional password reset/change.
2. Admin-target authorization boundary.
3. Refresh-token reuse/race fail-closed behavior.
4. Production metrics/CORS/cookie compose hardening.
5. Argon2 bounds and local compose/testcontainer reproducibility.
